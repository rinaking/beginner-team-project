## A. 시작 전 구축 (순서대로, 한 번만)

### A-1. GitHub 저장소 생성

GitHub → 오른쪽 위 **+** → **New repository**

| 칸 | 값 |
| --- | --- |
| Repository name | `beginner-team-project` (영문 소문자-하이픈) |
| Description | 한 줄 설명 |
| Public / Private | **Public** |
| Add a README file | 체크 |
| Add .gitignore | 템플릿 **Python** |
| Choose a license | **MIT** |

→ **Create repository**. (이미 있으면 건너뜀)

### A-2. 초기 파일 커밋

로컬로 받아서 팀 공용 기준 파일을 먼저 넣습니다.

```bash
git clone https://github.com/rinaking/beginner-team-project.git
cd beginner-team-project
```

넣을 것: `README.md` · `.gitignore` · `environment.yml` · `.github/PULL_REQUEST_TEMPLATE.md`

```bash
git add .
git commit -m "chore: 프로젝트 초기 구성"
git push origin main
```

> `.env`(비밀값)는 절대 커밋하지 않습니다. 한 번 들어가면 이력에 남습니다. `.gitignore` 에 `.env` 가 있는지 먼저 확인.

### A-3. 저장소 설정 — 병합 방식

**Settings → General → 아래로 스크롤 → Pull Requests**

| 항목 | 설정 |
| --- | --- |
| Allow merge commits | 해제 |
| Allow squash merging | 체크 (이것만) |
| Allow rebase merging | 해제 |
| Automatically delete head branches | 체크 |

### A-4. 저장소 설정 — `main` 보호 규칙

**Settings → Rules → Rulesets → New ruleset → New branch ruleset** (구버전은 **Branches → Add rule**)

1. **Ruleset Name**: `main`
2. **Enforcement status**: **Active**
3. **Target branches**: **Add target → Include default branch** (= `main`)
4. **Branch rules** 에서 아래를 체크:

| 규칙 | 설정 | 막아주는 것 |
| --- | --- | --- |
| Require a pull request before merging | 체크 | `main` 직접 push |
| └ Required approvals | **1** | 리뷰 없이 병합 |
| └ Dismiss stale approvals when new commits are pushed | 체크 | 승인 뒤 몰래 바꾸기 |
| └ Require conversation resolution before merging | 체크 | 리뷰 코멘트 미해결 병합 |
| Require status checks to pass | (CI 있을 때만) 체크 + 검사 이름 추가 | 검사 안 끝난 코드 병합 |
| Require linear history | 체크 | 병합 커밋 난립 |
| Block force pushes | 체크 | 이력 통째 날리는 사고 |
| Restrict deletions | 체크 | `main` 삭제 |

5. **Allowed merge methods**: `Squash` 만 남김
6. **Create** / **Save changes**

> **함정** — "Require status checks" 를 켜고 **존재하지 않는 검사 이름**을 필수로 걸면, CI 가 한 번도 안 돌아서 **모든 PR 이 영원히 병합 불가**가 됩니다. CI 워크플로를 먼저 push·1회 실행한 뒤, 그때 생긴 정확한 검사 이름을 넣으세요.

#### 팀장도 규칙을 따를까?

- **Bypass list** 는 처음엔 비워 두세요. 단, 이 경우 팀장도 초기 세팅·긴급 수정을 PR 로 해야 합니다.
- 팀장이 초기에 직접 push 해야 하면 Bypass list 에 본인(Role: Repository admin)을 잠깐 추가했다가, 팀이 안정되면 뺍니다.
- 승인 1개 필수이고 **본인 PR은 본인이 승인 불가** → 리뷰 가능한 팀원이 최소 2명 되기 전까지 팀장 우회가 필요할 수 있습니다.

### A-5. 팀원 초대

**Settings → Collaborators → Add people**

1. 팀원에게 **GitHub 아이디(username)** 를 받는다 (이메일 아님).
2. 검색창에 아이디 입력 → 선택 → 권한 **Write** → **Add to repository**.
3. 팀원은 이메일 또는 `github.com/notifications` 에서 **Accept**.

> 초대를 수락 안 한 팀원은 `git push` 시 **`Permission denied`** 가 납니다. 가장 먼저 확인할 증상.

### A-6. (선택) CI 워크플로

`.github/workflows/ci.yml` 을 넣어 커밋·PR 마다 lint·테스트를 자동 실행합니다.

- 넣은 뒤 push → **Actions** 탭에서 1회 실행 확인
- 그 다음 A-4 의 "Require status checks" 에 방금 생긴 검사 이름을 넣어 필수화

### A-7. 협업 판 깔기

| 도구 | 위치 | 용도 |
| --- | --- | --- |
| PR 템플릿 | `.github/PULL_REQUEST_TEMPLATE.md` | PR 본문 서식 (작업내용·구현기능·테스트결과·체크리스트) |
| Labels | **Issues → Labels** | `bug` `feature` `blocked` 분류 |
| Projects (칸반) | **Projects → New project → Board** | Todo / In progress / In review / Done |
| Milestones | **Issues → Milestones** | "중간 점검" "발표" 로 기한 묶음 |

> 처음엔 PR 템플릿 + Projects 보드 두 개면 충분.

## B. 브랜치 전략 결정 & 공지

### 선택 기준

| | GitHub Flow | Git Flow |
| --- | --- | --- |
| 팀 규모·릴리스 | 소규모 · 잦은 통합 | 큰 팀 · 정기 릴리스 |
| 복잡도 | 낮음 | 높음 · 버전 롤백 잦음 |
| 브랜치 | `main` + `feature/*` | `main` `develop` `feature/*` `release/*` `hotfix/*` |

### 우리 팀 결정 — GitHub Flow

`main` 직접 push 금지 · `feature/*` 에서 작업 → PR → 승인 1 → Squash 병합 → 브랜치 삭제.

팀 공지 문구 (그대로 복사):

> 우리 팀 브랜치 전략은 **GitHub Flow** 입니다. `main` 직접 push 금지, 모든 작업은 `feature/*` → PR → 리뷰 1명 승인 → Squash 병합 → 브랜치 삭제. 자세한 건 협업 지시서 B·D 참고.

## C. 스프린트 운영

### 매일

1. **데일리 체크인** — 어제/오늘/막힌 것. 막힌 사람 먼저 돕기.
2. **PR 큐 확인** — **Pull requests** 탭. 리뷰 안 된 지 24시간 넘은 PR 없게.
3. **리뷰·병합** — C-3.
4. **`main` 상태 확인** — 마지막 병합 후 `main` 이 정상 동작하는지.

### 매주

- 중간 점검 — 기능별 진행률, 통합 상태.
- 일정 리스크 — 늦어지는 기능 재배치, 범위 축소 판단.

### C-3. 리뷰·병합 (팀장이 직접)

1. PR → **Files changed** 탭에서 코드 확인
2. 괜찮으면 **Review changes → Approve**
3. **승인 1개 + (CI 있으면) 검사 통과 + 대화 해결** → **Squash and merge → Confirm → Delete branch**
4. 병합은 **팀장 또는 PR 작성자**가 한다

### C-4. 충돌 중재

- 기준을 팀장이 정해준다 (보통 먼저 병합된 쪽 기준).
- 해결은 **해당 브랜치 주인**이 하고, 팀장은 방향만 정리.
- 같은 파일을 자주 건드리는 구조면 담당을 다시 나눈다.

## D. 코드 리뷰 (팀장이 리뷰할 때)

- **정확성 → 엣지 케이스 → 테스트 유무** 순으로 본다.
- "이거 이상해요" 대신 **"여기서 X면 Y되니 Z로 바꾸면 어떨까요"**.
- 취향(대문자·띄어쓰기)은 도구(ruff 등)에 맡기고 로직에 집중.
- **Suggestion** 기능(코멘트창 `±` 아이콘)으로 고칠 코드를 직접 제안하면 상대가 버튼으로 바로 반영.
- 칭찬도 남긴다 ("이 부분 깔끔하네요").
- 리뷰어 미지정 PR엔 `@아이디` 멘션으로 직접 요청.

## E. 팀장이 자주 밟는 함정

| 함정 | 왜 위험 | 예방 |
| --- | --- | --- |
| 본인 PR을 본인이 승인하려 함 | GitHub 가 막음 → 혼자면 병합 불가 | 리뷰 가능 팀원 2명 이상, 아니면 초반 Bypass 허용 |
| `main` 직접 push | 리뷰 없이 깨진 코드 유입 | 초기 세팅 외엔 팀장도 PR |
| `git push --force` | 팀원 이력이 날아감 | 절대 금지, 브랜치 보호로도 차단 |
| 대용량/비밀 파일 최초 커밋 | 이력에 영구 잔존 | A-2 전에 `.gitignore` 먼저 |
| CI 검사 이름 불일치 | 모든 PR 병합 불가 | 워크플로 1회 실행 후 정확한 이름 지정 |
| 병합 방식 미통일 | 이력이 사람마다 다른 모양 | A-3 에서 Squash 만 |
| 팀원 초대 미수락 | 그 팀원 push 불가 | 초대 후 "수락했는지" 확인 |
| 브랜치 오래 방치 | main 과 벌어져 충돌 폭발 | "하루·이틀 안에 PR" 규칙 |

## F. 마무리

- **코드 프리즈** — 발표 며칠 전부터 새 기능 금지, `fix` 만. 팀에 공지.
- **최종 README** — 프로젝트 개요 / 폴더 구조 / 실행 방법(환경 구성·학습·평가) / 결과 / 팀원별 역할.
- **(선택) 릴리스 태그** — `git tag -a v1.0 -m "첫 발표"` → `git push origin v1.0`, 또는 GitHub **Releases → Draft a new release**.
- **회고** — 잘된 점 / 아쉬운 점 / 다음엔. Git 관점도 (충돌 빈도, 리뷰 속도).
