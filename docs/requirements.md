# 요구사항 명세서 (김혜린 작성, 9/11 / 9/14 업데이트)

9/11에 로컬 데이터(`sprint_ai_project1_data/`)를 직접 열어보고 확정한 내용. 처음에 팀이 가정했던 수치랑 꽤 달라서 아래에 정리해둠. 9/14에 763개 annotation 전수 집계로 한 번 더 정정한 부분도 있음(2-1).

## 1. 문제 정의
- 입력: 알약 사진 1장(.png, 976×1280)
- 출력: 사진 속 각 알약의 class(약 이름) + bbox(x,y,w,h, 픽셀 절대좌표), 이미지당 최대 4개
- 검증: Kaggle Private Competition (`ai14-level-project`)

## 2. 데이터 실측
처음 가정과 실측값이 꽤 다르다.

| 항목 | 기존 가정 | 실측값 |
|---|---|---|
| 클래스(약 종류) 수 | ~2000종 | 56종 |
| 학습 이미지 수 | ~200장 | 232장 |
| 고유 장면(알약 조합) 수 | ~40개 | 114개 |
| 장면당 이미지 수 이유 | 상하/좌우 반전 | 촬영 각도 차이(반전 아님, 2-1 참고) |
| 이미지당 알약 수 | 최대 4개 | 2개 7장 / 3개 151장 / 4개 74장 |
| 테스트 이미지 수 | ~800장 | 842장 (파일명 1.png~1500.png 중 일부, 정답 없음) |

클래스 커버리지 문제는 예상보다 작을 것 같다(2000종이 아니라 56종이니까). 대신 촬영 조건 다양성에 대한 일반화가 새 과제로 떠올랐음. 외부 데이터 수집 우선순위를 "커버리지 확장"에서 "촬영 조건 다양성 확보"로 조정할지는 9/16 게이트에서 논의.

### 2-1. EDA 재정정 (9/14, annotation 763개 전수 집계)
- 이미지당 알약 개수는 3~4개가 아니라 2~4개다. 2개 7장(3.0%), 3개 151장(65.1%), 4개 74장(31.9%). "항상 3~4개"라고 가정하고 후처리에서 개수를 강제하면 안 됨 — 지금 제출 CSV가 이미지당 무조건 4개를 채우는 버그(6번 항목)랑 바로 연결되는 근거.
- "촬영조건 차이"라고 불러온 게 사실은 카메라 각도(`camera_la`)만 변하는 거였다. `light_color`(주백색), `back_color`(연회색 배경)는 763개 annotation 전부 같은 값 — 실제로는 안 변함. 각도는 70°/75°/90° 세 종류(각각 237/249/277회), `camera_lo`는 항상 0. 그러니까 학습 데이터의 촬영조건 다양성은 "조명·배경·각도"가 아니라 각도 하나뿐이었던 것. 조명·배경이 실제 서비스 환경이랑 다를 가능성은 여전히 남아있지만 학습셋만 봐서는 확인이 안 됨.
- 고유 조합 114개 중 각도 사본이 1장뿐인 조합 36개, 2장 38개, 3장 40개 (36+38×2+40×3=232, 맞아떨어짐).
- 클래스 불균형이 심하다. 제일 많은 클래스 "일양하이트린정 2mg"(id 3351)이 전체 763개 중 153회(20%)를 차지. 반대로 3회밖에 없는 클래스도 여럿. 56종 중 상위 몇 종이 인스턴스 상당수를 가져가는 구조라 소수 클래스는 학습 샘플이 절대적으로 부족함.
- 해상도는 학습·테스트 전부 976×1280으로 동일. 리사이즈 배율만 통일하면 됨.

## 3. 라벨 포맷
- COCO 스타일 JSON인데, 이미지당 1개가 아니라 알약 1개당 JSON 파일 1개 (`train_annotations/<조합>_json/<약코드>/*.json`)
- 같은 이미지에 알약 개수만큼(2~4개) JSON이 따로 있어서 학습 전에 이미지 단위로 병합해야 함(강인호 전처리 1순위 작업, 완료)
- bbox = [x, y, width, height] 픽셀 절대좌표, 정규화 안 됨
- category_id = 실제 약 코드, category.name = 실제 약 이름 (예: "가바토파정 100mg")

## 4. 제약
1. 학습 데이터 232장 = 고유 조합 114개, 반전이 아니라 촬영 각도 차이
2. 클래스 56종 (AI Hub 전체 카탈로그 ~2000종과는 별개)
3. 시험 데이터(842장) 사용 금지 — 서버에서 채점
4. 데이터 증강 미승인 — 9/16 멘토링에서 허용 범위 확정 전까지 OFF
5. 금지 데이터: `TL_2_조합.zip`, `TS_2_조합.zip`

## 5. 평가지표 · 제출 포맷 (9/14 대회 페이지에서 직접 확인)
- 평가지표는 mAP@[0.75:0.95]. 로컬 검증에서 이미 쓰던 IoU 범위(0.75~0.95)랑 정확히 일치해서 따로 조정할 필요는 없음.
- 제출 포맷: `annotation_id, image_id, category_id, bbox_x, bbox_y, bbox_w, bbox_h, score` (한 행 = 객체 1개). image_id는 파일명 숫자, annotation_id는 행 단위 임의 고유값, category_id는 실제 약 코드.
- 참고로 대회 참가자 16명 중 실제 참여 7명, 팀은 2개뿐인 소규모 비공개 대회.

## 6. Public Score 이상 신호 (9/14 발견)
로컬 CV mAP는 0.41~0.48대인데 Kaggle Public Score는 0.086~0.124밖에 안 나온다. 제출 CSV를 뜯어보니 이미지당 confidence 상관없이 무조건 4개를 채우고 있었음(실제로는 이미지마다 2~4개인데). 4순위로 뽑힌 예측의 76%가 confidence 0.3 미만이라 대부분 오탐(FP)으로 보임. "무조건 top-4"가 아니라 confidence threshold(0.3~0.5)로 먼저 거르고 최대 4개로 자르는 방식으로 바꿔야 할 것 같음.

`~/초급팀프로젝트/src/predict_to_submission.py`(YOLOv8용)는 conf/iou/max_det으로 먼저 필터링 후 자르는 정상 구조라 이 버그는 없음.

**9/14 오후 버그 원인 확정** (`feature/initial-modeling` 브랜치, 유영관 푸시):
- SSD300(`VGG16_SSD300.ipynb` 17번 셀): 모델 생성 시 `ssd300_vgg16(..., detections_per_img=4)`로 아예 모델 레벨에서 항상 4개 반환하도록 고정돼 있었음. 뒤의 `score_thresh=0.2` 필터는 모델 내부의 느슨한 기본 임계값(0.01)으로 이미 뽑힌 4개에 적용돼서 사실상 무력화됨.
- RetinaNet(`RetinaNet_ResNet50_FPN_v2.ipynb` 36번 셀): 모델 자체는 정상, 제출 코드에서 `score_thresh=0.05`(사실상 통과)로 거른 뒤 `scores.argsort(descending=True)[:4]`로 무조건 상위 4개를 취함. RetinaNet은 4순위 평균 confidence가 0.56으로 SSD300(0.27)보다 높아서 피해가 상대적으로 작았음.
- 수정 방향: SSD300은 `detections_per_img` 제거/상향 + 후처리에서 threshold→cap 순서로. RetinaNet은 `score_thresh`를 0.3~0.5로 올린 뒤 최대 4개로 자르기.
