# 분석 보고서 아웃라인 (초안, 김혜린 9/14)

Definition of Done이랑 결과 평가 기준 맞춰서 뼈대만 잡아봄. 9/17에 모델 슬라이드/보고서(데이터·EDA) 쓸 때 이거 가져다 쓰면 될 듯.

## 1. 문제 정의
헬스잇(Health Eat) 시나리오 — 사용자가 찍은 알약 사진에서 이름+위치 인식. 이미지 1장당 최대 4개 알약의 class + bbox를 찾는 Object Detection 문제고, Kaggle Private Competition에서 mAP@[0.75:0.95]로 채점됨. (requirements.md 1, 5번 참고)

## 2. 데이터 개요
학습 232장은 고유 조합 114개가 촬영 각도만 바꿔서 여러 장씩 찍힌 것(사본 1장인 조합 36개, 2장 38개, 3장 40개 — 더해보면 232장 딱 맞음). 클래스는 56종, 라벨은 원래 알약 한 개당 JSON 하나씩(763개)이라 강인호가 이미지 단위로 병합함. 테스트는 842장인데 정답이 없어서 쓸 수 없고, 해상도는 학습이랑 똑같이 976×1280.

763개 annotation을 다 세어보니 몇 가지 다시 잡아야 할 게 나왔다. 일단 클래스 불균형이 생각보다 심하다 — 제일 많은 클래스(일양하이트린정 2mg)가 153번 나오는데 이게 전체의 20%고, 반대로 3번밖에 안 나오는 클래스도 여럿이다. 56종 중 18종이 인스턴스 5개 이하라 소수 클래스는 학습 샘플 자체가 너무 적음. class weight나 oversampling 얘기가 나올 수밖에 없는 상황.

이미지당 알약 개수도 원래 "3~4개"라고만 알고 있었는데 실제로는 2개짜리 사진도 7장 있다(3개 151장, 4개 74장). 이게 왜 중요하냐면, 제출 파일 만들 때 이미지당 개수를 고정해버리면 틀린다는 얘기라서 — 지금 나온 점수 이상신호(5번에 적음)랑 바로 연결됨.

그리고 "촬영조건이 조명·각도로 다양하다"고 써놨던 것도 확인해보니 반은 틀렸다. light_color랑 back_color는 763개 전부 값이 똑같아서 실제로 변하는 게 아니고, 진짜 바뀌는 건 카메라 각도(camera_la, 70/75/90도) 하나뿐이었다. 실서비스에서 사용자가 다른 조명·배경으로 찍으면 어떻게 될지는 이 데이터만 봐선 알 수가 없다는 뜻이기도 하다.

bbox는 이미지 대비 면적비 중앙값이 4.3%라 작은 편이고, 종횡비는 중앙값 1.0으로 대체로 정사각형에 가깝다.

(참고로 `~/초급팀프로젝트/DATASET.md`에 "test에 train에 없는 클래스가 있다"는 메모가 있던데, test는 라벨이 없어서 이걸 확인할 방법이 없다. 누가 어떻게 확인했는지 불명이라 일단 그대로 믿진 않는 걸로.)

## 3. 전처리
강인호가 `최초_모델링(전처리 수정본).ipynb`에서 알약 단위 JSON을 이미지 단위로 병합하는 부분을 손봤다. 파일명 stem으로 그룹핑하고, 학습 시작 전에 한 번만 병합해두는 식으로 바꿔서 매 스텝 JSON 다시 읽는 걸 없앴음. 증강은 9/16 게이트 전까지 계속 꺼둔 상태.

전처리 파이프라인 그림이랑 병합 전/후 검증 수치는 아직 안 만듦.

## 4. 모델
베이스라인은 유영관이 만든 torchvision SSD300 + VGG16 전이학습(SGD, lr 1e-3, StepLR, 30 epoch). 여기에 오늘부터 YOLOv8n도 따로 돌려보는 중 — `~/초급팀프로젝트`에 이미 만들어져 있던 YOLO 데이터셋 그대로 써서.

백본 비교표(RetinaNet, Faster R-CNN 등 — 유영관 9/17 태스크)랑 최종 모델 선정 이유는 아직.

## 코드 관련 메모

강인호가 병합 로직 바꾼 부분(`build_image_records`) — 원래는 Dataset이 이미지 하나 꺼낼 때마다 JSON을 다시 열어서 합쳤는데, 이제는 학습 시작 전에 한 번에 다 읽어서 저장해두고 거기서 꺼내 쓰는 식. 클래스 매핑도 이 과정에서 같이 만들어서 따로 또 도는 코드를 없앴다.

YOLOv8 학습 옵션 중에 눈여겨볼 것들:
```
imgsz=1280 epochs=80 patience=20 batch=8 device=mps
optimizer=AdamW cos_lr=True lr0=0.001 weight_decay=0.0005 seed=42
mosaic=0 mixup=0 ... fliplr=0 flipud=0  (증강 전부 0)
```
imgsz를 1280으로 크게 잡은 건 알약 bbox가 원래 작아서(면적비 4.3%) 해상도를 너무 줄이면 안 될 것 같아서. 증강 값들 다 0으로 박아둔 건 9/16 전까지 증강 쓰면 안 되는 걸 코드로도 강제해두려고. patience=20은 20 epoch 동안 val mAP가 안 오르면 자동으로 멈추는 옵션이라 데이터가 232장밖에 없는 상황에서 과적합 방지용.

제출 파일 뽑는 `predict_to_submission.py`는:
```python
model.predict(image, conf=args.conf, iou=args.iou, max_det=args.max_det)
```
이렇게 confidence로 먼저 거르고, NMS(iou)로 겹치는 박스 정리한 다음, 남은 것 중 최대 max_det개만 가져가는 구조라 이미지마다 개수가 다르게 나옴. 지금 쓰고 있는 SSD300 제출 파일 쪽은 이 구조가 아니라서(5번 항목의 그 버그) 여기랑 비교해보면 차이가 확실히 보임.
